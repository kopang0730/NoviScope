# NoviScope Collaboration Guide

这份文档用于约束小组成员和 AI 工具共同参与 NoviScope 开发时的协作方式。目标不是增加流程负担，而是避免项目变成不可维护、不可审查、不可复现的代码堆。

## 基本原则

- 先写清楚问题，再写代码。
- 小步提交，小 PR 合并。
- 每个行为变化都应该有测试或明确的人工验证记录。
- AI 可以辅助实现，但不能替代人对设计、风险和结果负责。
- 涉及科研结论、实验结果、文献引用和数据安全的变更必须保留证据链。

## Issue 使用规则

每个非平凡任务都应该先开 issue。issue 至少说明：

- 背景和目标
- 预期行为
- 不做什么
- 验证方式
- 相关风险

适合拆 issue 的粒度：

- 一个 API 功能
- 一个 agent 能力
- 一个数据模型变更
- 一个实验 runner 能力
- 一份文档或模板

不建议把多个大模块放到一个 issue 里，例如“实现完整科研系统”。

## Pull Request 规则

PR 应该回答：

- 改了什么
- 为什么这样改
- 有哪些风险
- 怎么验证
- 是否影响已有 API、数据库或 agent 权限

PR 不应该包含：

- 未说明来源的大段 AI 生成代码
- 未验证的论文结论
- API key、私有数据、实验日志、checkpoint
- 与任务无关的格式化或重构

推荐按风险拆 PR：

| 风险等级 | 示例 | 合并要求 |
| --- | --- | --- |
| Low | 文档、文案、测试补充 | 链接/命令检查，至少一名 reviewer |
| Medium | API 响应、provider 设置、artifact 下载、普通 UI 状态 | 自动测试 + API 或浏览器 smoke |
| High | agent prompt、stage gate、auth、密钥处理、科研结论规则 | 测试 + 信任边界说明 + 维护者复核 |
| Critical | 本地代码执行、数据上传/下载、GPU 任务、数据库迁移 | 先开设计 issue，明确回滚方案和权限边界 |

如果一个 PR 同时触碰多个 High/Critical 区域，应拆分；拆不开时必须在 PR 中解释为什么。

## AI 生成代码规范

允许使用 AI 写代码，但必须满足：

- 代码经过人类阅读和测试。
- PR 描述中说明哪些部分由 AI 辅助。
- 不接受“AI 说可以”的验证方式。
- 不接受无法解释的数据模型、状态机、权限控制或安全逻辑。
- 不把未验证的文献观点、实验结果写进 README、论文或报告。
- 不允许 AI 在没有人工确认的情况下把本地代码、私有数据、实验日志上传到外部服务。
- 不允许 AI 把未检查的 arXiv、博客、论坛内容当成顶会/顶刊证据。
- 不允许 AI 通过大规模无关重构掩盖一个小功能变更。
- AI 输出必须能被当前代码、命令输出、API 响应、截图或文献来源验证。

AI 辅助开发推荐流程：

1. 人先定义目标、边界和验收标准。
2. AI 负责实现或整理候选方案。
3. 人检查 diff、数据流、权限、测试和实际运行结果。
4. PR 中记录验证命令和人工观察。
5. reviewer 按正常工程标准审查，不因为“AI 生成”降低要求。

如果 AI 产物无法解释、无法测试、无法追溯来源，应该删除或重写，而不是继续堆补丁。

## 代码审查重点

审查优先级：

1. 是否会导致数据泄露或密钥泄露。
2. 是否破坏 quest/stage 状态机。
3. 是否让 agent 获得过宽权限。
4. 是否把未验证结论当作事实。
5. 是否缺少测试。
6. 是否引入难以维护的大文件或重复逻辑。

审查时可以直接拒绝以下变更：

- 把 `pending` 或 `needs_review` 内容展示成已验证结论。
- 绕过 demand review、idea selection、experiment review 等人工 gate。
- 未经说明扩大 agent 工具权限，尤其是网络、文件写入、代码执行。
- 在测试中硬编码真实 API key、真实用户数据或真实私有路径。
- 新增超过一个职责的大文件，且没有拆分理由。

## Definition of Done

一个任务完成至少需要：

- 功能实现或文档更新已经提交。
- `uv run ruff check .` 通过。
- `uv run pytest` 通过，或说明失败原因。
- 对外行为经过 API、CLI 或文档检查。
- GitHub issue 或 PR 中有验证记录。

按变更类型补充验证：

| 变更类型 | 最低验证 |
| --- | --- |
| 后端 API | 目标测试 + `uv run pytest` + 一个 API smoke |
| agent/prompt | 结构化输出测试 + 幻觉/未验证结论防护测试 |
| 前端 UI | `npm --prefix web run build` + 桌面/移动浏览器 smoke |
| 文档 | 检查命令、链接和实现状态是否与当前代码一致 |
| 部署脚本 | 干净工作区测试、失败路径说明、回滚方式 |

## 研究可信度约束

NoviScope 的最终目标是辅助科研，不是批量生成看似完整的内容。因此：

- 文献结论必须能追溯到来源。
- 实验结果必须能追溯到代码、参数、数据和日志。
- 论文结论必须由 evidence auditor 认可后才能进入正式草稿。
- 需求真实性验证未通过前，不应进入高成本实验阶段。

实验结果状态约定：

- `verified`：可以作为待引用事实进入 brief 或论文草稿，但必须保留 run id、artifact、数据集、baseline 和指标。
- `needs_review`：只能进入人工复核清单，不能进入正式结果叙述。
- `rejected`：只能作为负面记录或失败分析来源，不能作为支持性证据。
- 没有真实实验记录时，Results/Conclusion 必须保持占位或明确写作限制。

## 多人协作习惯

- 同一功能只保留一个主 PR，避免多个同学和多个 AI 同时改同一文件。
- 开始工作前先看当前 open PR，确认是否已有相同方向。
- 如果必须基于另一个未合并 PR 开发，应在 PR 描述中说明依赖关系。
- 不要在别人的分支上直接改动，除非对方明确要求。
- 遇到冲突时优先保留可追踪的数据结构和测试，而不是保留更大的 diff。

## 数据与服务器安全

- API key 只能通过 provider 配置入口进入系统，不写入代码、Markdown、截图或日志。
- 课题组数据、企业数据、试卷图像、用户填写内容、训练日志和 checkpoint 不进 git。
- 实验阶段可以下载开源代码、配置环境、运行脚本，但默认不能上传本地代码或数据。
- 如果新功能需要外部上传、远程执行或公开链接，必须先写清楚数据边界和人工确认点。
- 服务器部署脚本应支持非 root 用户路径，不假设 sudo 权限。
